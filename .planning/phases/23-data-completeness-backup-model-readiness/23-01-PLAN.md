<objective>
Extend `engine/health_check.py` from a 2-series tail-freshness checker into a full-history, 4-series (gex_snapshots, surface_history, vol_index, oi_history) gap scanner across all 3 tickers (SPY/QQQ/IWM), per D-02/D-03/D-04/D-05 in 23-CONTEXT.md. This is the foundational scanner that Plan 23-04 (model-readiness depth audit) reuses for session counting — it must land first.

Purpose: today's `check_health()` only compares the latest stored date to the expected session (a tail check) and only covers 2 of the 4 series. It cannot catch a session that went silently missing mid-history (e.g. a scheduler failure weeks ago that has since self-healed) — exactly the gap ROADMAP Phase 23 success criterion #3 requires catching.

Output: `engine/data/validation.py` gains a `list_snapshot_dates()` helper; `engine/health_check.py` gains a full-history scanner wired into the existing `--strict`/`--json` CLI surface (no new dashboard panel, per D-01); `engine/tests/test_data_health.py` gains coverage for gap-detection and CBOE-holiday semantics.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| parquet store on disk → health_check scanner | Files written by the daily collection job; not attacker-controlled, but can be corrupted by disk/process interruption |
| health_check `--json` output → CI logs | Only dates, counts, and status strings — no secrets, no PII |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23-01 | Tampering | `_series_dates()` parquet reads | mitigate | Each underlying reader (`list_snapshot_dates`, `list_available_dates`, `load_vol_index`, `list_oi_dates`) already wraps reads in try/except returning an empty result + a `print()` warning on corruption — a corrupted file surfaces as a 0-date series, which `_full_history_scan` correctly reports as a full gap range (fails `--strict`) rather than silently passing green |
| T-23-02 | Denial of Service | `full_history_report()` runtime in CI | mitigate | `dates_by_series` computed once per ticker (not once per series-pair comparison); each reader does a single vectorized `pd.read_parquet(columns=[...])` call, not a per-date read, per Pitfall 4 in 23-RESEARCH.md |
| T-23-03 | Information Disclosure | `--json` output content | accept | Output is dates/counts/status strings only; no dashboard exposure (D-01), stays in GH Actions logs (private to repo owner) |
</threat_model>
