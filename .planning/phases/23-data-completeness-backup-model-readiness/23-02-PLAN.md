<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions secrets → boto3 env vars | `OCI_ACCESS_KEY_ID` / `OCI_CUSTOMER_SECRET_KEY` cross from GH's encrypted secret store into process environment (wiring happens in Plan 23-03; this plan's modules only consume them) |
| Oracle Object Storage → local disk (restore) | Downloaded bytes are treated as trusted parquet, but the download channel or bucket could theoretically deliver corrupted/wrong data |
| Restore destination (`out/`) | A live, in-use directory on the Oracle VM or a developer's machine — restoring into it is destructive if done carelessly |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23-04 | Spoofing / Information Disclosure | `_s3_client()` credential handling | mitigate | Credentials read only via `os.environ["OCI_ACCESS_KEY_ID"]` / `os.environ["OCI_CUSTOMER_SECRET_KEY"]`; never printed, never written to a file, never passed as a CLI argument (only bucket/region/dest/flags are CLI args) |
| T-23-05 | Tampering | `restore_from_oci()` writing into `dest` | mitigate | `RestoreSafetyError` raised whenever `dest` already contains files and neither `--dry-run` nor `--force` is passed — a restore run by mistake against a live populated `out/` aborts instead of overwriting |
| T-23-06 | Tampering | Parquet integrity after download | mitigate | Every downloaded `.parquet` file is round-tripped through `pd.read_parquet()` immediately after download; a corrupted file raises `RestoreCorruptionError` (loud failure) instead of being silently written into the store |
| T-23-SC | Tampering (supply chain) | `boto3` package addition | accept | Already vetted in 23-RESEARCH.md Package Legitimacy Audit — PyPI, 8+ yrs, 100M+/wk downloads, [OK] slopcheck verdict, Approved — no blocking checkpoint required per the gate (only ASSUMED/SUS packages require one) |
</threat_model>
