  <behavior>
    - Test 1: yesterday_state="out", today_rank >= entry_band, n >= credibility floor → returns ("entry", "in_entry").
    - Test 2: yesterday_state="in_entry", today_rank >= escalate_band → returns ("escalation", "in_escalate") (re-fire only on escalation, per D-04).
    - Test 3: yesterday_state="in_entry", today_rank stays between exit_band and escalate_band → returns (None, "in_entry") — no re-fire, no flicker.
    - Test 4: yesterday_state="in_entry" or "in_escalate", today_rank < exit_band (exit_band < entry_band, hysteresis) → returns (None, "out").
    - Test 5: today_rank >= entry_band BUT n < MONITOR_CREDIBILITY_FLOOR_SESSIONS → returns (None, "out") always, regardless of rank — alert suppressed, D-08's ship-time consequence (chain metrics stay silent until ~2027-05).
    - Test 6: Three independent rank_kinds (level_deep, level_1yr, change) on the same metric×ticker can each be in a different band_state simultaneously — verify by running the function three times with three different (rank, state) inputs and confirming no cross-talk (pure function, no shared state).
  </behavior>
  <action>
Implement `engine/monitor/hysteresis.py` with:

`check_alert_transition(today_rank: int | None, n: int, yesterday_state: str, entry: int, escalate: int, exit_: int, credibility_floor: int = config.MONITOR_CREDIBILITY_FLOOR_SESSIONS) -> tuple[str | None, str]`

States are plain strings: "out", "in_entry", "in_escalate" (matches MonitorRow.band_state_* field type). Logic per RESEARCH.md Pattern 3: out→in_entry on rank>=entry (FIRE "entry"); in_entry→in_escalate on rank>=escalate (FIRE "escalation"); any in_* → out on rank<exit_ (no fire, hysteresis exit). If `today_rank is None` or `n < credibility_floor`, always return `(None, "out")` regardless of prior state — an under-sample metric never enters or stays in an alert band (D-08).

This function is called three times per metric×ticker per day by monitor_store.py (Task 2) — once each for level_rank_deep, level_rank_1yr, and change_rank — using that day's independently-tracked band_state_deep/band_state_1yr/band_state_change as `yesterday_state`. Do not implement that orchestration here — this task is the pure state-transition function only.

Note: entry/escalate/exit band values are NOT hardcoded in this file — they are passed in as parameters, sourced from config.py constants that Plan 03's calibration CLI populates. Until Plan 03 runs, callers may pass provisional values (e.g. entry=97, escalate=99, exit_=87) documented as "provisional pending calibration" — do not invent a different provisional scheme without noting it.
  </action>
