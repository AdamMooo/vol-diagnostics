<objective>
Ship the permanent calibration CLI that replays the ECDF ranker + hysteresis state machine over all stored metric history, reports alert episodes/week for a grid of candidate bands and hysteresis widths, and — since this is the first time it runs — use its output to replace the provisional MONITOR_ALERT_BAND_* placeholders (Plan 02, Task 3) with real calibration-derived values, documented with the replay evidence per D-06.

Purpose: D-05's ~1 episode/week false-alarm budget and D-06's requirement that bands come from empirical replay, not vibes. This CLI is a permanent, re-runnable deliverable — not a one-off analysis — so it can be re-run as chain-metric history deepens (D-08's ~2027-05 milestone).
Output: `engine/monitor/calibration.py` (CLI + programmatic API) + config.py bands updated with replay evidence in the comment (calibration date, history depth, chosen eps/week).
</objective>

  <behavior>
    - Test 1: `replay_metric(history: pd.Series, entry: int, escalate: int, exit_: int, credibility_floor: int) -> list[dict]` walks the series day-by-day (expanding window: rank each day against all prior days only, no look-ahead), calling compute_level_ranks + check_alert_transition at each step, and returns the list of alert events (each `{"date":, "alert_type":, "rank":}`) produced over the whole replay.
    - Test 2: On a synthetic series with one clear spike (e.g. constant baseline + single 3-day excursion above the 97th percentile), replay_metric produces exactly 1 "entry" event, not one per day the excursion persists (hysteresis working as intended within the replay, not just in isolated unit tests).
    - Test 3: `count_episodes_per_week(events: list[dict], total_sessions: int) -> float` converts a raw event count to an episodes/week rate using `len(events) / (total_sessions / 5)` (5 trading sessions/week, matches RESEARCH.md Pattern 6).
    - Test 4: `calibrate(candidate_bands=[90,95,97,98,99], hysteresis_gaps=[5,10,15]) -> dict` runs replay_metric across ALL METRIC_INVENTORY pairs for every (entry, gap) combination (escalate = midpoint between entry and 99, per RESEARCH.md Pattern 6) and returns `{"results": [{"band_entry":, "band_escalate":, "band_exit":, "episodes_per_week":, "flicker_ratio":}, ...]}` sorted by how close episodes_per_week is to the D-05 target (~1/week).
    - Test 5: A metric with no history (load_metric_series returns None) is skipped in the replay without crashing the whole calibration run.
  </behavior>
  <action>
Implement `engine/monitor/calibration.py`:

`replay_metric(history, entry, escalate, exit_, credibility_floor=config.MONITOR_CREDIBILITY_FLOOR_SESSIONS) -> list[dict]` — iterate `i` from `credibility_floor` (or from 1 if shorter, honoring D-08 "ranks always computed" even pre-floor for visibility) to `len(history)`; at each `i`, treat `history.iloc[:i+1]` as "history so far" and `history.iloc[i]` as "today's value"; call `ranker.compute_level_ranks` (deep lookback = all of `history.iloc[:i]`) then `hysteresis.check_alert_transition` carrying state across iterations. Collect every non-None alert_type into the returned list with its date (use the Series' index) and rank.

`count_episodes_per_week(events, total_sessions) -> float` — simple ratio per Behavior Test 3.

`flicker_ratio(events) -> float` — count how many "entry" events occur within 3 sessions of a prior "entry"/"escalation" for the SAME metric (re-firing due to bouncing near the band) divided by total distinct episodes; used to pick the hysteresis gap that minimizes this (Pitfall 3 in RESEARCH.md — "same event firing twice ≈ 1-2 days apart" is the flicker signature to collapse).

`calibrate(candidate_bands: list[int] = [90,95,97,98,99], hysteresis_gaps: list[int] = [5,10,15]) -> dict` — for each `(metric_name, ticker)` in `schema.METRIC_INVENTORY`: `history = metrics.load_metric_series(ticker, metric_name)`; skip (continue) if None or too short. For each `(band_entry, gap)` combination: `band_exit = band_entry - gap`; `band_escalate = band_entry + (99 - band_entry) // 2`; run `replay_metric`; aggregate episodes/week and flicker_ratio across ALL metrics for that band combination (not per-metric — D-05's budget is "across the whole monitor"). Return the aggregated `results` list, each entry a dict with band_entry/band_escalate/band_exit/episodes_per_week/flicker_ratio, sorted by `abs(episodes_per_week - 1.0)` ascending (closest to the ~1/week target first).

CLI entry point (`if __name__ == "__main__":`) mirroring engine/run_gex.py's argparse pattern: `--candidate-bands` (comma-separated ints, default "90,95,97,98,99"), `--hysteresis-gaps` (comma-separated ints, default "5,10,15"), `--dry-run` (print the report table, do not touch config.py — since this is a human-in-the-loop CLI, it NEVER auto-writes config.py; it prints a config-ready snippet per RESEARCH.md Pitfall 2 for the human/executor to copy in). Print a markdown table of results plus a top recommendation line.
  </action>
