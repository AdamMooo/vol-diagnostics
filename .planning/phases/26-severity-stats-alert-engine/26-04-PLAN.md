<objective>
Fix four correctness defects found in Phase 26 verification (26-VERIFICATION.md / 26-REVIEW.md), all independent of the calibration-methodology rework in 26-05: CR-01 (stale-value fallback writes yesterday's value under today's date), WR-04 (a one-day rank=None I/O blip collapses an active alert state, manufacturing a duplicate entry alert on recovery), WR-05 (compute_change_rank is off-by-one when today's value is not already the series tail), and WR-06 (surface-evolution horizon silently coupled to the change-rank k constant).

Purpose: These are shipped-code correctness bugs, not design gaps — 26-01/02/03's architecture is sound but these four spots violate the monitor's own stated contracts (today-dated rows must be today's actual values; hysteresis state should survive transient I/O failures; change-rank math should be correct regardless of caller assumptions; unrelated constants should not be silently coupled).
Output: Patched `engine/monitor/monitor_store.py`, `hysteresis.py`, `ranker.py`, `metrics.py`, a new `engine/config.py` constant, and updated/added tests proving each fix.
</objective>

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-26-06 | Tampering (data integrity) | `monitor_store.compute_and_save_monitor_rows` | mitigate | Date-guard the stale-value fallback (CR-01) so a delayed/failed upstream save can never be silently persisted and ranked as if it were today's observation |
| T-26-07 | Denial of Service (spurious alert) | `hysteresis.check_alert_transition` | mitigate | Hold prior alert state on a transient `None` rank (WR-04) instead of resetting, so a one-day I/O blip cannot manufacture a duplicate "entry" alert on data recovery |
