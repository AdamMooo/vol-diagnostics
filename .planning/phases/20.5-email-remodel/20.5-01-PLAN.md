<objective>
Give the email remodel (Plan 03) two new pieces of real data to display: an actual fetch-time timestamp (not the date-only `as_of` field) and an OI-weighted filter-drop ratio showing how much of the raw chain got excluded by the `min_oi`/`max_iv` quality filters.

**Design decision (resolves the PATTERNS.md "No Analog Found" flag):** `ChainSnapshot.as_of` is a `datetime.date` -- it cannot support the target display format `Snapshot 2026-05-11 16:15 ET`. Rather than downgrading the display to date-only (losing the time-of-day fact entirely), this plan adds a genuine `fetched_at` capture in `load_chain()` at the point the CBOE response is actually received. This is a one-field, one-line addition -- low cost -- and means the header line in Plan 03 shows real data, not a fabricated timestamp. `as_of` is left untouched (still drives DTE/T_years elsewhere).

Purpose: Thread genuinely new data (fetch timestamp, filter-drop ratio) through the existing "compute once in the pipeline, read many times in renderers" seam so `report.py` (Plan 03) never does I/O or math -- it only formats values already sitting on the summary dict.
Output: `ChainSnapshot` gains `fetched_at` + `filter_drop_pct`; `compute_ticker()`'s `summary` dict gains `as_of`, `fetched_at`, `filter_drop_pct`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| CBOE CDN -> load_chain() | Existing, unchanged boundary -- this plan adds no new network call, no new endpoint, and no new external input. It only reads two values (open_interest, and the wall-clock time of an already-successful response) that are already inside the existing trusted fetch path. |
| load_chain() -> compute_ticker() -> summary dict | Internal, in-process only. No serialization boundary, no untrusted input. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-20.5-01 | Tampering | load_chain() filter-drop counters | accept | raw_oi_total/kept_oi_total are derived purely from already-validated `int(opt.get("open_interest") or 0)` casts (existing code) -- no new parsing of untrusted strings, no new attack surface beyond what load_chain() already exposes. |
| T-20.5-02 | Information Disclosure | fetched_at / filter_drop_pct in summary | accept | Both are internal computed diagnostics (fetch time, quality-filter ratio) with no PII or secret material; email recipient is the same PM who already receives spot/GEX/IV data in the same message. |
| T-20.5-03 | Denial of Service | filter_drop_pct division | mitigate | Guarded with `if raw_oi_total > 0 else None` -- division by zero on an empty/degenerate chain returns None (existing cold-start-safe pattern) rather than raising and crashing the daily run. |

This plan introduces no new user-facing input, no new external service call, and no template/HTML rendering -- it is a pure data-computation change inside an existing, already-trusted fetch/compute pipeline. No high-severity findings.
