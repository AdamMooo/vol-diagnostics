## Warnings

### WR-01: `test_compute_oi_wiring.py` — `load_evolution` not mocked; test makes real filesystem call

**File:** `engine/tests/test_compute_oi_wiring.py:63-81`

**Issue:** `_make_mock_result()` mocks 17 of the 18 external dependencies in `compute_ticker`, but `load_evolution` is not mocked. `compute.py` imports it as a module-level name (`from engine.surface.surface_evolution import load_evolution`) and calls it at line 183. The test patches `compute_mod.vrp_percentile`, `compute_mod.load_history`, etc., but has no corresponding `mock.patch.object(compute_mod, "load_evolution", ...)`. The result is that every test in `TestExpiryOiDfKey` and `TestIsTopDecile` reads from `out/surface_evolution.parquet` on the real filesystem. If that file is absent, truncated, or schema-mismatched, `load_evolution` may raise and the test will fail with an unrelated error. In CI or a clean checkout without `out/` artifacts, this silently depends on graceful error handling inside `load_evolution` rather than the test being properly isolated.

**Fix:** add the missing mock alongside the others in `_make_mock_result()`:
```python
mock.patch.object(compute_mod, "load_evolution",
                  return_value=pd.DataFrame()),
```

### WR-02: `compute.py:97` — `is_top_decile = False` scalar assignment produces object dtype in the else-branch

**File:** `engine/compute.py:97`

**Issue:** When all OI values are zero, the code takes the else-branch:
```python
s_df["is_top_decile"] = False
```
Assigning a Python scalar `False` to a DataFrame column gives `bool` dtype in pandas >= 1.0 but `object` dtype in some environments. The truthy-path at line 95 produces a proper `bool` Series (result of a comparison). The dtype inconsistency between branches means `result["s_df"]["is_top_decile"].dtype == bool` (which `test_is_top_decile_is_bool_dtype` asserts) is only exercised for the truthy path — the zero-OI branch is never checked for dtype. The downstream consumer in `analytics.py` is safe (`chain_df[chain_df["is_top_decile"]]` works for either dtype), but the contract on the returned dict is quietly inconsistent.

**Fix:** be explicit in the else-branch:
```python
else:
    s_df["is_top_decile"] = pd.array([False] * len(s_df), dtype=bool)
```
or simply:
```python
else:
    s_df["is_top_decile"] = False
    s_df["is_top_decile"] = s_df["is_top_decile"].astype(bool)
```

## Info

### IN-01: `report.py:217` — `import datetime as _dt` inside `iterrows()` loop

**File:** `engine/report/report.py:217`

**Issue:** `_oi_summary_table()` imports `datetime` as `_dt` inside the `for _, row in top3.iterrows():` loop. The loop is at most 3 iterations (head(3)) so the runtime cost is negligible, but putting an import inside a loop is confusing and non-idiomatic. `datetime` is already imported at the module top level (line 3: `import datetime`).

**Fix:** remove the inner import and use the module-level `datetime`:
```python
expiry_str = (
    datetime.datetime.strptime(str(expiry_raw), "%Y-%m-%d").strftime("%b %d")
    if expiry_raw else str(expiry_raw)
)
```

### IN-02: `app.py:709-719` — `_fmt_oi` and `_fmt_delta_oi` redefined on every Streamlit render cycle inside the ticker loop

**File:** `app.py:709-719`

**Issue:** `_fmt_oi` and `_fmt_delta_oi` are defined as local functions inside `with st.expander(...)`, which itself is inside `for ticker in selected_all:`. Streamlit re-runs the full script on every interaction, so these functions are re-created on every render for every ticker. This is a mild code smell — closures over `prior_oi_map` that is immediately consumed mean there is no actual bug, but hoisting `_fmt_oi` (which has no closure dependencies) to module level would be cleaner.

**Fix:** move `_fmt_oi` to module scope (it has no dependencies on local state). Leave `_fmt_delta_oi` local since it closes over `prior_oi_map`. No behavioral change.
